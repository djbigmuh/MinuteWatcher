# Contributing to MinuteWatcher

Thank you for your interest in contributing to MinuteWatcher! To maintain high code quality and app stability, we follow a strict testing and architectural policy.

## Development Environment Requirements
- **JDK 21** (Temurin 21.0.12+) is the mandatory version for all developers.
- The Detekt/KSP toolchain is highly sensitive to the JDK version. Higher versions (like **JDK 25**) must not be present in the system `PATH`.
- Set your JDK path locally via the `JAVA_HOME` environment variable or in your user-level
  `~/.gradle/gradle.properties` (using `org.gradle.java.home`). Do not commit this setting to the project repository.
- Machine-specific JVM properties (including `-Duser.home` overrides when Windows profile paths contain non-ASCII
  characters or spaces) must be placed solely in user-level `%USERPROFILE%\.gradle\gradle.properties`. Machine-specific
  properties in the project `gradle.properties` file are strictly prohibited.

### SDK Location on Windows (local.properties)

- Configure `sdk.dir` using forward slashes (`/`), escaped drive colon (`\:`), and `\uXXXX` escapes for non-ASCII
  characters. Alternatively, use an ASCII-only path without spaces.
- Reason: Android Lint treats unescaped Windows path formats as `PropertyEscape` errors and fails the build.
- Rule: `local.properties` is not committed; verify its formatting whenever regenerated by IDE.

## Testing Policy

Every contribution must be accompanied by appropriate tests. We follow the **Testing Pyramid** approach:

### 1. Unit Tests (~80%)
The majority of our tests should be unit tests. They must cover:
- **Core Logic:** Any calculators (`BillingPeriodCalculator`), date utilities, and formatting tools.
- **Data Models:** State transitions and logic within data classes.
- **Repositories:** Logic within `SimLimitsRepositoryImpl`, `SimUsageRepositoryImpl`, `AppSettingsRepositoryImpl`, etc. (using Mockito for dependencies).
- **ViewModels:** UI state mapping and user action handling.
- **Resource Integrity:** Consistency between language arrays in `arrays.xml`.

### 2. Integration Tests (~15%)
Used for components that interact with the Android system or multiple modules:
- **Background Work:** `InitialSetupWorker` and `UsageCheckWorker` should be tested using `WorkManager` testing tools.
- **Database Migrations:** `IdentityMigrationService` must have tests verifying data integrity across versions.
- **Trackers:** `CallTracker` and `TrafficTracker` logic.

### 3. UI Tests (~5%)
Automated UI tests should cover critical user paths:
- Onboarding flow.
- Setting minutes and data limits.
- Core widget layout rendering.

Certain modules require 100% coverage of their public API:
- `:core:model`: All utilities and calculators.
- `:core:common`: `PermissionManager`.
- `:core:android`: `OperatorResolver`, `WidgetUiMapper` (must test all `WidgetLayoutMode` scenarios).

## The "Bug-Fix" Rule
> [!IMPORTANT]
> Every bug fix must include a regression test that demonstrates the bug and verifies that the fix prevents it from recurring.

## Static Analysis
We enforce strict static analysis. Every developer MUST run verification before committing:
`./gradlew ktlintCheck detekt lintDebug testDebugUnitTest :app:assembleDebug`: Full verification (ktlint + detekt + lint + tests + build). Use before completing any task.

Your code must pass:

- **Detekt (2.0.0-alpha.6):** Baseline files are not used in the project. Any detekt or lint warning must be fixed
  directly in the source code; adding suppressions via baseline files is strictly forbidden.
- **Lint:** The build will fail on any lint error or warning. `MissingTranslation` is a fatal error.
- **Ktlint:** Code style must follow the established Kotlin standards.

### False-Positive Analysis Warning Justification Rule
An analysis warning identified as a false positive is permitted to be preserved only if accompanied by an English comment formulating the justification criterion. Suppressions must have the minimum possible scope. File-level suppressions and baseline files are strictly prohibited.

Permitted categories of false-positive suppressions include:
- Hilt production bindings with single implementations
- Hilt entry points without direct class references
- Variant-specific implementations selected via Hilt source set bindings
- Declarations utilized solely through code generation (e.g., KSP processors or annotation processors)

## Architectural Guidelines
- **Dependency Inversion:** Feature modules must never depend directly on `:core:data`. Use interfaces defined in `:core:domain`.
- **Modularity:** Keep `:core:model` free of Android dependencies to ensure high-speed testing.
- **DI:** Use Hilt for dependency injection and provide specific qualifiers (`@IoDispatcher`, etc.) instead of hardcoded dispatchers.
- **Dispatchers:** All components must use injected dispatchers via Hilt qualifiers (`@IoDispatcher`, `@MainImmediateDispatcher`). Direct usage of `Dispatchers.IO` or `Dispatchers.Default` is STRICTLY FORBIDDEN everywhere except in `DispatchersModule` and the infrastructure class `AppLogger`.
- **Machine-readable Errors:** When classifying errors in `TrackingStatus.Error`, always use `type` and `code`. Branching logic based on message text (`message`) is STRICTLY FORBIDDEN, as messages are intended only for logs and the user.
- **Resource Dependencies:** Dependency on `:core:resources` is mandatory if module sources or its manifest reference resources of that module, because resource merging is not reflected in source-based dependency analysis.
- **Dependency Declarations:** Dependency declarations must not be removed based on analysis reports that consider only source code references, without verifying resource references, manifest, and test source sets' classpath.

## Non-Stable Dependencies
As a general rule, we prefer stable releases. However, some non-stable versions (Beta/Alpha) are currently used for specific reasons:

- **AGP (Preview)** and **Detekt (Alpha)** are explicitly permitted until stable
  versions with equivalent fixes are available.
- Before introducing a new non-stable dependency, agree its addition with the project owner and document the reason in `docs/dependencies.md` and as a comment in `gradle/libs.versions.toml`.

## Version Management

- **Gradle Version Catalog:** When updating `AGP` (Android Gradle Plugin) or `Kotlin` versions, you MUST update both
  `gradle/libs.versions.toml` and `gradle/build-logic.versions.toml` to keep the main project and build-logic in sync.

## Build Performance & Unit Test Stability

To maintain a reliable testing environment on Windows and prevent issues with native runtimes or file locking, the
following configurations are centralized in the build setup and must not be duplicated in
individual module build scripts:

- **Test JVM Settings (`maxParallelForks = 1`, `forkEvery = 1`, JVM arguments, Robolectric properties)**:
  Centralized in the convention plugin `build-logic/src/main/kotlin/minutewatcher.test-infrastructure.gradle.kts`,
  applied to all modules via convention plugins `minutewatcher.android-application`, `minutewatcher.android-library`,
  and `minutewatcher.android-test`.
    - `maxParallelForks = 1`: Prevents multiple JVMs from competing for system resources and native library locks.
    - `forkEvery = 1`: Ensures each test class runs in a fresh JVM, preventing side effects between test classes and
      avoiding issues with Robolectric native runtimes on Windows.
- **Android Test Options (`isReturnDefaultValues = true`, `isIncludeAndroidResources = true`)**:
  Configured centrally in `build-logic` convention plugins (`minutewatcher.android-application`,
  `minutewatcher.android-library`).
  `isReturnDefaultValues` allows plain JUnit tests to run without Robolectric for logic that doesn't strictly depend on
  Android constants or native behavior.

### Robolectric vs. Plain JUnit

- **Prefer Plain JUnit:** For utilities in `:core:common`, `:core:domain`, and `:core:model`. These tests run in a pure
  JVM environment and are very fast.
- **Use Robolectric:**
    - Tests involving **DataStore** or **WorkManager**.
    - Tests depending on **Android Constants** (e.g., `TelephonyManager.EXTRA_STATE_*`). Mocked SDKs return `null` for
      these strings when `isReturnDefaultValues` is true, causing logic failure.
    - Tests with **complex Android logic** or UI components (Compose Previews).

### Windows-Specific Caveats

- **DataStore:** When running plain JUnit tests on Windows that use DataStore, ensure each test method uses a **unique
  filename** (e.g., using `UUID.randomUUID()`) to avoid `IOException` during file renaming due to OS-level file locking.
- **Paths:** Avoid spaces or non-ASCII characters in the project path (e.g., `C:\Users\Username`). This can cause
  `NoSuchFileException` in Robolectric native runtime loading.

## Naming and History Policy

### 1. Commit Messages

Commit messages must use the imperative mood and clearly describe the change and its motivation.

- **Prohibited:** External task/audit IDs (e.g., `TZ-*`, `Task N`, `#123`), links to task files, mentions of specific AI
  assistants, or project phases (e.g., `Phase 1`).
- **Prohibited:** Meaningless messages (single numbers, one-word summaries).
- **Explanation:** The commit body should explain "why" a change was made, not "which task" it fulfills.

### 2. Code Comments and KDoc

Comments must describe the code, its contracts, invariants, and reliability criteria.

- **Prohibited:** References to the work history, such as "added in Task 5", "fixed during audit", or dates of
  modification.
- Git history serves as the record of changes; source code must remain clean of process artifacts.

### 3. Test Naming

Test names must be behavioral and describe the scenario and expected outcome (e.g.,
`recover cancellation completes promptly`).

- **Avoid:** Task numbers or direct references to private field names if the same logic can be expressed through
  observable behavior.

### 4. Concurrency Cleanup Rule

To prevent deadlocks and ensure system liveness:

- Cleanup operations in `finally` blocks must be either non-suspending (e.g., atomic sets/removals) or strictly
  time-limited.
- **Forbidden:** Waiting for a `Mutex` inside `NonCancellable` unless it's guaranteed to be available quickly.
- Atomic flags (`AtomicBoolean`, `AtomicReference`) should be preferred for gating logic and must not be wrapped in
  mutexes.

### 5. Test Discipline

- **Timeouts:** Every `await()` or `join()` in a test must be wrapped in `withTimeout` with a descriptive message to
  avoid infinite hangs.
- **Encapsulation:** Reflection-based access to private members for testing is strictly forbidden.
- **Fakes over Mocks:** For complex suspendable collaborators, prefer providing a `Fake` implementation over a `Mock`,
  as un-stubbed mocks can silently change the execution flow.

### 6. Instruction Files

External task files, instruction documents, and audit requirements must never be committed to the repository.

## Release Signing

- **Generating Key:** To generate a release key, run the following command from the repository root:
  `keytool -genkeypair -v -keystore app/release.keystore -alias <alias> -keyalg RSA -keysize 4096 -validity 10000`
- **Environment Variables:** Release signing requires three environment variables:
    - `MINUTEWATCHER_STORE_PASSWORD`
    - `MINUTEWATCHER_KEY_ALIAS`
    - `MINUTEWATCHER_KEY_PASSWORD`
- **Security Rule:** `release.keystore` and passwords must never be committed to version control. The key backup must be
  safely stored by the project owner.
- **Unsigned Build Fallback:** If `release.keystore` or any of the required environment variables are absent, the
  release build produces an unsigned APK (`app-release-unsigned.apk`). No debug key fallback is used for release builds.
